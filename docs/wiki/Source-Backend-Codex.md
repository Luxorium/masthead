# server/backends/codex/

**Role:** the Codex backend. It runs the person's own signed-in Codex CLI through `codex app-server` and turns what Codex says into the same neutral session events as the Claude Code backend. Masthead never reads Codex's auth files and never bundles a copy of the CLI. The research behind it, with the evidence, is `docs/plans/0.2.0/codex.md`.

| File | What it holds |
|---|---|
| `index.ts` | `CodexBackend` (detect, models, the shared process) and `CodexSession` (one agent = one Codex thread); `CODEX_CAPS`, `CodexOptions` (`path`, `env`, `dataDir`, and for tests `runCli`, `spawnAppServer`); re-exports `MIN_VERSION`. |
| `cli.ts` | Plain commands: finding the binary (`findCodex`), `--version` (`parseVersion`, `versionAtLeast`), `login status` (`parseLogin`), the model catalogue rebuild (`prepareCatalog`, `withoutMultiAgent`, `catalogArgs`), the `debug prompt-input` check (`nativeToolsFor`, `promptTools`, `nativeAgentTools`), running commands (`runCli`) and starting app-server as a process tree (`makeSpawnAppServer`, `spawnAppServer`). |
| `rpc.ts` | `RpcPeer`: JSON-RPC 2.0 over newline-delimited JSON, both directions. |
| `families.ts` | The model order for the generated Codex team. |
| `generate-protocol.mjs` | Regenerates `protocol/` from the installed Codex. |
| `protocol/` | Vendored TypeScript types generated by `codex app-server generate-ts --experimental` (358 files from codex-cli 0.172.0, see `protocol/VERSION`). Only the types the adapter imports and what they import are kept. |
| `testing/fake-app-server.ts` | A scripted stand-in for the CLI and app-server, for tests only. |


## Limits of the Codex backend

What a Codex agent cannot do that a Claude Code agent can, all from `index.ts` (header comment and `CODEX_CAPS`):

- **Effort cannot change while an agent works.** `setEffort()` stores the level, and it is sent with the next `turn/start` (`liveEffort: false`).
- **No background tasks.** Codex runs a detached command as an ordinary one and never wakes the agent when it ends (`background: false`).
- **`max` and `ultra` are never sent.** They are left out of every model's levels (`NEVER`).
- **Codex's own extras are off:** its sub-agents (`features.multi_agent`, `multi_agent_v2`, and the catalogue rebuild below), image generation and goals. The team rules hold only if Masthead starts every agent.
- **Compaction runs as a turn of its own.** Codex sends no `thread/compacted` notice for it, so the first turn to start after the request is taken as the compaction and reported only as compacted ([Compaction](#compaction-compact)).
- `codex app-server` is marked experimental by Codex itself.

## How Codex is driven

- **One app-server process per `CodexBackend`**, that is per Masthead server, shared by every agent of every conversation; each agent is one thread on it. It starts lazily on the first `open()` or `models()` (`ensureServer()`), and if it dies every open session gets `exited` and the next `open()` starts a new one. Its environment is the `spec.env` of the session that started it, or the backend's own `env` when `models()` started it (threads cannot have their own).
- `startServer()` (`index.ts:204`) first rebuilds the model catalogue (below), then runs `codex app-server -c model_catalog_json="<file>"`.
- **Handshake:** request `initialize` with `clientInfo {name:'masthead', title:'Masthead', version:'0.2.0'}` and `capabilities {experimentalApi: true, requestAttestation: false}`, then the notification `initialized`. `experimentalApi` is what allows `dynamicTools`.
- **`rpc.ts`:** `RpcPeer` numbers its own requests, matches responses by id, passes notifications (no id) to `onNotification` and server requests (method and id) to `onRequest`, whose return value or thrown `RpcError` is written back. Lines that are not JSON are skipped. `close(reason)` fails every waiting request with code -32000; later requests fail at once with "Codex app-server is not running.". Write errors on a dead process are swallowed.
- Notifications are routed to a session by `params.threadId` (or `params.thread.id`); server requests by `params.threadId`. A server request with no matching session gets -32601, except `mcpServer/elicitation/request`, which is declined.

## Detection: `detect()`

`index.ts:131`, in order (the `BackendInfo` always carries `minVersion: '0.172.0'`):

1. **Find the binary** (`findCodex`, `cli.ts:81`; or `CodexOptions.path`): `MASTHEAD_CODEX`, then each `PATH` folder (`codex`, or `codex.exe` / `codex.cmd` on Windows), then `~/.local/bin/codex`, `/usr/local/bin/codex`, `/usr/bin/codex`, `/opt/homebrew/bin/codex`. None: "Codex was not found. Install it and sign in with `codex login`, then restart Masthead."
2. **`codex --version`**, first `x.y.z` in the output (a non-zero exit or no version: "Could not run <path> --version."). Below `MIN_VERSION = '0.172.0'` (`cli.ts:19`): not available, "Codex X is too old; Masthead needs 0.172.0 or later.".
3. **Tested range** `TESTED = /^0\.172\./` (`cli.ts:21`). Outside it the backend stays usable but sets `warning`: "Codex X has not been tested with Masthead (tested: 0.172.x)." The warning is passed on in the `BackendInfo`.
4. **`codex login status`** (`parseLogin`, `cli.ts:102`): "not logged in / logged out / no credentials" → signed out (not available, "Codex is not signed in. Run `codex login`."); exit 0 with "logged in" → signed in; anything else → `null` (unknown, still usable). Auth files are never read.
5. **Catalogue rebuild and check** on the first model whose `visibility` is not `hide`/`hidden`, else the first model (next section). Any error from it makes the backend unavailable with that message.

Every command runs through `runCli` with stdin closed (Codex waits on an open stdin) and a 60 s timeout.

## Codex's own sub-agents: the catalogue rebuild

Codex gives current models a `multi_agent_version`, and that field, not a feature flag, puts its `collaboration.*` tools (spawn_agent, send_message, wait_agent, …) in front of the model. Masthead's team rules forbid them, so:

- **`prepareCatalog()`** (`cli.ts:164`) runs `codex debug models` (the person's own catalogue), copies it with `multi_agent_version: null` on every model and writes it to `model-catalog.json` (mode 0600) in a private folder (made with mode 0700), by default `$TMPDIR/masthead-codex-<uid>/` (`CodexOptions.dataDir` overrides it). It fails with "codex debug models failed: …", "… did not print JSON." or "… listed no models.". It is rebuilt on every app-server start and on every `detect()`. The process is started with `-c model_catalog_json=<file>` (`catalogArgs`).
- **`nativeToolsFor()`** (`cli.ts:189`) runs `codex debug prompt-input -c model_catalog_json=… -c model="<model>" hi`, which renders what the model would see **without calling it**. `promptTools()` reads the names from the `additional_tools` item (namespaced, e.g. `collaboration.spawn_agent`); `nativeAgentTools()` keeps any `collaboration.*` or any name ending in `spawn_agent`, `wait_agent`, `followup_task` or `interrupt_agent`. If the rendering shows no tools at all it throws "codex debug prompt-input showed no tools; the check cannot be trusted.".
- **Where the check refuses:**
  - in `detect()`: "Codex's own sub-agent tools could not be switched off (<names>), so a Codex team could break the team rules." (backend unavailable);
  - in every session start, once per model per process (`checkModel`, `index.ts:235`, cached; a failed check is forgotten so it is retried): "Codex's own sub-agent tools are still offered to <model> (<names>); a Codex team cannot run." The session fails with that as its `exited` failure.
- **Second lock:** every thread's config also sets `features.multi_agent` and `features.multi_agent_v2` to false.
- **Fallback (`police()`, `index.ts:792`):** should an `item/started` of type `collabAgentToolCall` or `subAgentActivity` (kind `started`) arrive anyway, the session remembers the child thread ids, reports the activity "Stopped one of Codex's own sub-agents", queues a note for the next turn ("(Masthead: Codex's own sub-agent tools are not available in this team. Use spawn_agent and send_message instead.)") and interrupts the turn. This happens once per turn. A child thread's next `turn/started` is interrupted too (`foreignThread`).

## `models()`

`index.ts:153`. Pages through `model/list {includeHidden: false, cursor}` on the shared process.

- Models with `hidden` are left out (even if returned).
- `efforts`: Masthead's levels (low, medium, high, xhigh) that the model lists in `supportedReasoningEfforts`. `max` and `ultra` (`NEVER`, `index.ts:81`; ultra is Codex's "automatic task delegation") are never offered; `nativeEffort` maps each level to the same name.
- `label` is `displayName` (else the id); `description` is copied when present; `default` from `isDefault`.
- `contextWindow` and `order` come from the rebuilt catalogue entry whose slug equals the model's `model` or `id`: `context_window` and `priority`. `priority` is Codex's model-picker order, not a capability rank.

## The generated Codex team

- `families.ts`: `CODEX_FAMILY_ORDER = ['astra', 'sol', 'terra', 'luna']` (`families.ts:9`), most capable first. `parseCodexModel()` reads ids shaped `<prefix>-<version>-<family>` (e.g. `gpt-6.2-astra` → family astra, version [6, 2]). `codexTeamModels()` (`families.ts:32`) keeps the **newest version per family**, puts the known families in that order, then the newest of each unknown family in catalogue order (`order`, then list order). An id without the shape is its own family.
- The profile itself is built in `server/backends/registry.ts` (`codexProfile`, `registry.ts:143`): the first four models of that list become tiers `codex:0` … `codex:3` with the shape in `TIER_SHAPE` (`registry.ts:124`): lead xhigh, max 1, not lean; then xhigh / max 3, high / max 4, medium / max 4, all lean. Each effort is lowered to the highest level the model supports (`effortFor`); labels are the models' labels and colours follow `PALETTE` in order. With fewer models there are fewer tiers (one model: one tier). `generatedProfiles()` offers it only when Codex is available and the fake backend is not in use. Nothing in the code names a model; the person can edit the profile.

## Sessions: `open()` and `boot()`

`open()` returns a `CodexSession` at once and starts it in the background:

1. `ensureServer()`, then the sub-agent check for the model (above).
2. `thread/start` with `model`, `cwd`, `developerInstructions` (the agent's instructions; Codex's own are kept), `config`, the permission fields and `dynamicTools`; or, when `spec.resume` is set, `thread/resume {threadId, …same, excludeTurns: true}` (no `dynamicTools`: the thread keeps those it was started with).
3. The thread id is bound to the session and reported with `sessionStarted(threadId)`. Messages sent before this point open the first turn together.

**Missing thread:** a resume that fails with a message matching `no rollout found|not found|no such thread|unknown thread` (`index.ts:358`, in `boot()` at line 329) ends the session with `exited({failure, sessionMissing: true})`, before any `sessionStarted`, so the core starts fresh. Real Codex answers a missing thread with `{"code": -32600, "message": "no rollout found for thread id …"}`; the code matches the message, not the code.

**Per-thread config** (`config()`, `index.ts:370`), as dotted keys in `thread/start.config`:
- always: `features.goals`, `features.image_generation`, `features.multi_agent`, `features.multi_agent_v2` = false;
- lean tiers also: `features.apps` = false, and `mcp_servers.<name>.enabled` = false for every server listed by `config/read {cwd}`. If `config/read` fails the person's servers stay on.

**Permissions** (`permissions()`, `index.ts:388`):

| Masthead mode | Sent to Codex |
|---|---|
| `bypassPermissions` | `approvalPolicy: 'never'`, `sandbox: 'danger-full-access'` |
| `default` | `approvalPolicy: 'untrusted'`, `sandbox: 'workspace-write'`, `approvalsReviewer: 'user'` |
| `acceptEdits`, `auto` | `approvalPolicy: 'on-request'`, `sandbox: 'workspace-write'`, `approvalsReviewer: 'user'` |
| anything else (inherit) | only `approvalsReviewer: 'user'`; the person's own policy and sandbox apply |

`approvalsReviewer: 'user'` makes approvals come to Masthead instead of Codex's own reviewer model.

## Sending: `send(id, content)`

`index.ts:440`.

| State | What happens |
|---|---|
| no thread yet | held; all held messages open the first turn together |
| `compact()` running | queued; starts the next turn when the compaction ends |
| no turn | `turn/start {threadId, input, model, effort, clientUserMessageId}` (`clientUserMessageId` is the first message's id) |
| `turn/start` on its way | held, then steered once the turn id is known |
| turn running | `turn/steer {threadId, expectedTurnId, input, clientUserMessageId}` |

- **Consumed ids:** the ids of the messages that opened a turn, plus every successfully steered id, are returned in that turn's `turnEnded({consumed})`. A steered id is counted before the request, so a turn that ends meanwhile cannot drop it; if `turn/steer` fails (the turn ended, or Codex refuses to steer it) the id is removed again and the message opens or waits for the next turn.
- **`turn/start` failing** ends the turn at once with `turnEnded({consumed, text: '', error})` and starts any queued messages.
- **Effort and model** are sent on every `turn/start`; `setEffort()` / `setModel()` only store the value, so a change applies from the next turn (`liveEffort: false`).
- Messages queued behind a turn (and the adapter's own notes, which have no id) start the next turn when the current one completes.

## Team tools: `dynamicTools`

- Every `ToolDef` in `spec.tools` goes into `thread/start.dynamicTools` as `{type: 'function', name, description, inputSchema}`, with the **bare tool name** (no namespace).
- Codex calls one with the server request `item/tool/call {threadId, tool, namespace, arguments}`. The request is routed by `threadId` to the session that owns the thread, so the caller is the agent whose `ToolDef` runs; nothing in the arguments identifies it.
- `toolCall()` (`index.ts:803`) runs `tool.run(arguments)` and answers `{contentItems: [{type: 'inputText', text}], success}`; `success` is false when the text starts with `Error:`, when the tool throws (text `Error: <message>`), or when no tool has that name (text `Error: no tool named <name>`). No approval is asked for team tools.

## Approvals and questions

Each server request becomes one `askPermission()` call with an `AbortController` keyed by the JSON-RPC request id (`serverRequest()`, `index.ts:584`).

| Codex server request | `PermissionAsk` | allow | always | deny |
|---|---|---|---|---|
| `item/commandExecution/requestApproval` | kind `command`, tool `shell`, input `{command, cwd}`, description = `reason` | `accept` | `acceptForSession` if offered, else the offered `acceptWithExecpolicyAmendment` decision; `canAlways` false if neither | `decline` |
| `item/fileChange/requestApproval` | kind `file`, tool `apply_patch`, input `{changes, grantRoot}` (changes remembered from the item's `item/started`), description = `reason` | `accept` | `acceptForSession` | `decline` |
| `item/permissions/requestApproval` | kind `tool`, tool `permissions`, input = the asked permissions, description = `reason` | the asked `network` / `fileSystem`, scope `turn` | same, scope `session` | `{}` (nothing granted) |
| `item/tool/requestUserInput` | kind `question`, tool `request_user_input`, `questions` (single choice) | answers keyed by Codex's question id (matched from Masthead's answers by question text) | – | empty answers |
| `mcpServer/elicitation/request` | none | – | – | always `decline` |
| any other method | – | – | – | JSON-RPC error -32601 |

- An agent with `canAskPerson` false gets `{answers: {}}` for a question without a card.
- **Withdrawal:** the notification `serverRequest/resolved {requestId}` aborts that ask's signal, so the card goes away. `close()` aborts every open ask too. Masthead never answers `cancel`.

## Usage limits

`account/rateLimits/updated` carries one snapshot for the whole account, so it goes to **every** open session (`rateLimits()`, `index.ts:505`). For each of the `primary` and `secondary` windows present:

- `type` = `<limitId or 'codex'>:<windowDurationMins>m`, or `<limitId or 'codex'>:primary` / `:secondary` when the window has no duration;
- `utilization` = `usedPercent / 100`;
- `status`: `rejected` when the limit is reached (`rateLimitReachedType` set, or usedPercent ≥ 100) **and** usedPercent ≥ 100; `allowed_warning` when reached or usedPercent ≥ 80; otherwise `allowed`;
- `resetsAt` passed on unchanged when present, in seconds since the epoch (the same unit as Claude Code's).

A turn that fails with `usageLimitExceeded` or `rateLimitExceeded` ends with `apiError: 'rate_limit'`.

## Compaction: `compact()`

`thread/compact/start {threadId}` answers `{}` at once; Codex then runs the compaction as a turn of its own (`turn/started`, an item of type `contextCompaction`, `thread/tokenUsage/updated`, `turn/completed`). No `thread/compacted` notification came in a live check (codex-cli 0.172.0, gpt-6-luna, about 1.9 s), so `turn/completed` ends it. The first `turn/started` after the request, while no turn of Masthead's is running, is taken as the compaction turn: it produces no turnStarted, turnEnded, text or tool events (usage still goes through), fires `compacted()` once and resolves; failed or interrupted rejects. A session that is not open rejects with "The session is not open.", a busy one (turn running or starting, or already compacting) with "The session is busy."; closing, losing or disposing the session rejects a compaction under way. Messages sent meanwhile start the next turn after it.

## Context, images, interrupt, close

- **Context:** `thread/tokenUsage/updated` gives `last.totalTokens` (context in use) and `modelContextWindow`; `contextUsage()` returns the latest pair, or `{used: 0, max: 0}` before the first update. `usage.output` is the growth of `total.outputTokens` since the previous update. There is no cost in dollars.
- **Images in:** each image part is written to `$TMPDIR/masthead-codex-<uid>/images/<uuid>.<ext>` (mode 0600) and sent as `{type: 'localImage', path}`. The files are removed when the session closes, since Codex reads them when the turn runs. **Images out:** from `mcpToolCall` results (`image` content) and `dynamicToolCall` results (`inputImage` data URLs). Team tools only ever return text.
- **`interrupt()`:** `turn/interrupt {threadId, turnId}`; if `turn/start` is still on its way, the interrupt is sent as soon as the turn id is known.
- **`close('graceful' | 'now')`:** aborts open asks, unbinds the thread, then (for `now` with a turn running) `turn/interrupt`, then `thread/unsubscribe`; `ended` settles after that. No `exited` is reported. Threads are not deleted: they stay in the person's Codex history.
- **`ended`** settles on close, on failure, when the process is lost, and on `dispose()`.
- **Process lost:** every open session gets `exited({failure})` with the end of app-server's stderr and "codex app-server exited (<code or signal>)".
- **`dispose()`:** silences every session (no more events) and kills the process.

## Process-tree stop

The app-server runs shell commands for the model, so it is started as the root of its own process tree: `makeSpawnAppServer()` (`cli.ts:52`) uses `spawnTree()` and `killTree()` from `server/backends/proctree.ts`. On POSIX it gets its own process group (`detached`) and a stop sends SIGTERM to the group, then SIGKILL after a grace time (`KILL_GRACE_MS`, 3 s); on Windows a stop is `taskkill /T /F /PID <pid>`. `onExit` fires once, on `exit` or `error`, with the last 4000 characters of stderr.

## What is experimental

- `codex --help` marks `app-server` "[experimental]", and `dynamicTools` is an experimental part of its API (it needs `experimentalApi: true` at `initialize`). Either can change between Codex versions.
- The protocol is generated per Codex version. Masthead vendors the types from codex-cli 0.172.0 in `protocol/`, requires 0.172.0 or later, and warns outside 0.172.x. After a Codex upgrade, run `node server/backends/codex/generate-protocol.mjs` (it calls the installed `codex app-server generate-ts --experimental`, keeps only the imported types and adds `.js` extensions), then the Codex tests. The vendored types are only checked by `tsc`; nothing checks them against a running app-server at start-up.
- `codex debug models` and `codex debug prompt-input` are debug commands, and the sub-agent switch relies on the catalogue field `multi_agent_version`. If a later CLI renames it, the `prompt-input` check refuses to run a Codex team rather than letting the tools through.

## What was verified and how

**(a) Against real codex-cli 0.172.0** (bravo's research in `docs/plans/0.2.0/codex.md`, `gpt-6-luna` at low effort, on a ChatGPT Pro sign-in):

- the catalogue switch: with `multi_agent_version: null`, `debug prompt-input` shows no `collaboration.*` tools and the model in app-server cannot find them; feature flags and `agents.*` settings did not remove them;
- several active threads on one app-server; a native spawn raises no approval request; a background `nohup … &` command is not tracked and no turn follows.
- The live runs, written for this code: `test/codex.live.ts` runs the backend conformance suite (`test/backend-conformance.ts`, `live: true`) against the real CLI; `test/codex-team.live.ts` runs a real `App` with the registry's generated Codex team, every tier set to `gpt-6-luna` at low effort, where the lead starts one sub-agent with `spawn_agent` and passes on its report. Both delete every thread they created with `codex delete --force <id>`. `codex-team.live.ts` was run on 2026-11-27 against codex-cli 0.172.0 and passed: the generated team was Astra, Sol, Terra, Luna; the lead and one sub-agent ran on `gpt-6-luna`, the report reached the lead, and both threads were deleted. The result of `codex.live.ts` is not recorded here either (bravo ran it during development; ask before relying on it).

**(b) Only against the fake app-server** (`test/codex.test.ts` and `test/codex-proctree.test.ts`, 2 tests; 37 tests in all, all passed on 2026-11-27): file-change, permissions and question approvals; `serverRequest/resolved` withdrawal; the usage-limit turn and a rejected rate limit; MCP tool results with images; compaction; the process dying mid-turn and the next `open()` starting a new one; the `police()` fallback for a native sub-agent; resume of a missing thread as `sessionMissing`; the version / sign-in / switch-failure paths of `detect()`; paging and filtering in `models()`; the process-tree spawn and kill on POSIX and Windows (with fake process functions). ### Running the Codex live tests

They use real Codex usage on the signed-in account and are not part of `npm test`.

```sh
node --import tsx --test test/codex.live.ts   # conformance, 240 s per case
node --import tsx test/codex-team.live.ts     # a lead and one sub-agent
node --import tsx test/codex-app.live.ts      # approvals, images, stop, mixed team
```

`MASTHEAD_CODEX_MODEL` picks the model (default `gpt-6-luna`, the cheapest); `MASTHEAD_CODEX` the binary. Each session works in a temp folder. Cost: a trivial turn is about 16–19k input tokens (Codex's own prompt and tools), most of it cached; the team run is a few such turns. The fake-CLI tests run with `node --import tsx --test test/codex.test.ts` and need no account.

## Points to be aware of

- One process serves every Codex agent: if it dies, all of them end with `exited`, and its environment comes from the first session after a start.
- The missing-thread test matches the error **message**, and loosely (`not found` also matches), not the -32600 code.
- With the inherit permission mode Masthead still forces `approvalsReviewer: 'user'`, so cards appear even if the person's config uses Codex's auto reviewer.
- Rate-limit snapshots are account-wide and go to every session, so one update produces a notice per open session.
- `police()` interrupts a native child thread only on that child's next `turn/started`; a child turn already running when the item arrives is not interrupted.
- Threads Masthead creates stay in the person's Codex history (`codex resume`); nothing names, archives or deletes them.
- Effort changes never reach a running turn.
